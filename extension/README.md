# Onboarding X-Ray extension

Chrome extension (Manifest V3): service worker, content script, side panel and welcome page. Vite + TypeScript + React + Tailwind.

## Build

```
cd extension
npm install
npm run build
```

Output goes to `extension/dist/`. After changing the demo app, run `npm run analyze` at the repo root first: it refreshes `public/graph.json`, which the build bundles.

## Load unpacked in Chrome (139+)

1. Open `chrome://extensions`.
2. Turn on **Developer mode** (top right).
3. Click **Load unpacked** and select the `extension/dist` folder.
4. A welcome tab opens on install. Pin the extension (puzzle icon, then the pin).
5. Click the Onboarding X-Ray toolbar icon to open the side panel.

After a rebuild, click the reload icon on the extension's card in `chrome://extensions`.

## Try it

1. Start the demo store (see `demo-app/README.md`) and open http://localhost:5173.
2. Open the side panel, then Alt+click any element in the demo store. The side panel selects the matching component.
3. Or pick a component from the dropdown to see its chain.

The content script currently runs only on `http://localhost:5173/*` and `http://127.0.0.1:5173/*`.

## Layout

| Path | Purpose |
|---|---|
| `manifest.json` | MV3 manifest, copied into `dist/` |
| `src/background/` | Service worker: opens the side panel from the icon, opens the welcome page on install |
| `src/content/` | Alt+hover highlight, Alt+click sends the element's `data-source` to the side panel |
| `src/sidepanel/` | Side panel UI: X-Ray and Repo map tabs, React Flow chain diagram, steps with highlighted code |
| `src/welcome/` | Welcome page |
| `src/lib/graph.ts` | Load and query `graph.json` |
| `vite.config.ts` | Pages and service worker |
| `vite.content.config.ts` | Content script, built separately as one classic script |

## Icons

Placeholder icons are generated by `node scripts/make-icons.mjs` (run from `extension/`) into `public/icons/`. Replace the PNGs with real artwork any time.

## Firebase App Check (debug token)

`src/lib/firebase.ts` initialises Firebase and App Check (debug provider only). Values come from the repo-root `.env` (see `.env.example`).

A Chrome extension cannot run reCAPTCHA Enterprise (it loads a remote script, which Manifest V3 forbids), so App Check uses a **debug token**:

1. Build in debug mode: `npm run build:dev` (or `npm run dev` to rebuild on save), then reload the extension.
2. Open the side panel, right-click inside it, choose **Inspect**, open the **Console** tab.
3. Find `Firebase App Check debug token: <uuid>` (copy the uuid).
4. Register it in the Firebase console: **Build, App Check, Apps**, select `xray-extension`, three-dot menu, **Manage debug tokens**, **Add debug token**, paste, name it, **Save**. Or with the CLI: `firebase appcheck:debugtokens:create <uuid> --project onboarding-xray --app <app id>`.

The token is stored in the extension's IndexedDB, so it stays the same across reloads (it changes only if you clear the extension's site data or the unpacked extension's folder/ID changes). Never commit it. Debug mode is on in every build (dev, normal and submission), and `npm run build` and `npm run build:dev` both run `scripts/check-mv3.mjs`. `VITE_APPCHECK_DEBUG_TOKEN` pins one fixed token, but it is then baked into `dist/`, so never ship a build made with it.

## AI explanations (Firebase AI Logic hybrid inference)

Every step in the side panel has an **Explanation** area with an **Explain this step** button; **Summarize whole flow** explains the whole chain. Requests start only from a click.

| Mode (toggle in the panel header) | SDK mode | Behavior |
|---|---|---|
| Private only | `ONLY_ON_DEVICE` | On-device model only. No inference request, no Firestore cache, no Remote Config fetch. If the model is missing, or the prompt is too long, you get a clear message with **Download on-device model** and **Switch to Auto**. |
| Auto (default) | `PREFER_ON_DEVICE` | On-device when the model is ready and the prompt fits `on_device_max_chars`; otherwise the cloud. |
| Best quality | `PREFER_IN_CLOUD` | Cloud model, on-device as a fallback. |

Each answer shows a badge: green **On-device · private**, or blue **Cloud** with the reason (`model not downloaded`, `on-device unavailable`, `too long for on-device`, `Best quality mode`). The status pill shows **On-device ready**, **Downloading N%** or **Cloud only**. The choice is remembered in `localStorage`.

The code is in `src/lib/explain.ts` (mode logic, caches, prompts, unit-tested), `firebaseModel.ts` (the SDK call) and `onDevice.ts` (Chrome Prompt API availability and download).

**Cache (Firestore + anonymous Auth).** Answers are cached in memory and in the shared Firestore collection `explanations`, keyed by `sha256(prompt version + mode tier + layer + code)`. Best quality and Auto answers are cached separately. Anonymous sign-in happens lazily the first time the shared cache is used, never in Private only mode. The shared cache is for the bundled demo graph, whose code is public. Rules are in `firestore.rules` (signed-in users can read one entry and create new ones; no update, delete or list). They are **not deployed automatically**:

```
firebase deploy --only firestore:rules
```

**Remote Config keys** (all optional, in-app defaults): `on_device_max_chars` (4000), `prompt_version` (`v1`; bump to invalidate cached answers), `default_mode` (`auto`, used until the user picks a mode), `cloud_model` (`gemini-3.5-flash-lite`).

**App Check.** Firebase AI Logic rejects requests without a valid App Check token (`401 Firebase App Check token is invalid`), so register the debug token first (see above).

**On-device model.** Needs Chrome 139+ on a supported device. Check `chrome://on-device-internals`. Without it, everything works in Cloud mode.

## Submission build (zip for the Web Store and judges)

`npm run package:submission` (from the repo root, or `npm run package:submission` inside `extension/`) builds a zip you can upload. It differs from the other builds like this:

| | `npm run build` | `npm run build:dev` | **`package:submission`** |
|---|---|---|---|
| App Check provider | Debug token only | Debug token only | **Debug token only** |
| Debug token | generated in the browser | generated in the browser | **injected at build time from `XRAY_APPCHECK_DEBUG_TOKEN`** |
| reCAPTCHA code and site key in the bundle | no | no | **no** |
| Remote script URLs / eval / `new Function` | n/a | n/a | **none, verified by `scripts/check-mv3.mjs`** |

The build **fails** if `XRAY_APPCHECK_DEBUG_TOKEN` is missing or malformed. After building, `scripts/check-mv3.mjs --submission` parses every script and fails the build if it finds `eval`, `new Function`, `importScripts`, script injection, a remote script URL, a reCAPTCHA provider, a loosened content security policy, a missing manifest file, or the debug token anywhere except the JS bundle. It also fails if the injected token is not actually in the bundle. Then `scripts/make-zip.mjs` writes `extension/release/onboarding-xray-submission-v<version>.zip` (manifest at the zip root, no source maps, reproducible) and prints its SHA-256. `extension/release/` and `*.zip` are git-ignored.

### 1. Create a separate "judges" debug token

Use a **new token only for judges**. Do not reuse your own development token (`my-laptop`): it stays valid for your machine and must not be in a zip.

Either with the CLI (it generates the token and prints it once; copy it):

```
firebase appcheck:debugtokens:create --project onboarding-xray --app 1:69691650784:web:aaa7374f1253cb8a5ed685 --display-name "judges-2026" --no-save-local
```

or in the console: generate a UUID (`node -e "console.log(crypto.randomUUID())"`), then **Build, App Check, Apps, xray-extension, three-dot menu, Manage debug tokens, Add debug token**, paste it, name it `judges-2026`, **Save**.

### 2. Build the zip

The token must be in the environment of the build, never in a committed file.

```
# bash
XRAY_APPCHECK_DEBUG_TOKEN=<judges-token> npm run package:submission

# PowerShell
$env:XRAY_APPCHECK_DEBUG_TOKEN = "<judges-token>"; npm run package:submission
```

Or add `XRAY_APPCHECK_DEBUG_TOKEN=<judges-token>` to the git-ignored root `.env` (it is not a `VITE_` variable, so dev builds never read it).

### 3. Test the zip before uploading

Unzip it, open `chrome://extensions`, **Load unpacked**, pick the unzipped folder, open the side panel, pick Checkout, switch to **Best quality**, and click **Explain this step**. You should get a **Cloud** answer. If you get "the cloud service rejected this build's access token", the token is not registered (or was revoked).

### 4. Revoke the token after judging

```
firebase appcheck:debugtokens:list --project onboarding-xray --app 1:69691650784:web:aaa7374f1253cb8a5ed685
firebase appcheck:debugtokens:delete <debugTokenId> --project onboarding-xray --app 1:69691650784:web:aaa7374f1253cb8a5ed685 --force
```

Use the **debugTokenId** from the `judges-2026` row (the long id at the end of its resource name), not your own token's. Or in the console: **App Check, Apps, xray-extension, Manage debug tokens**, delete the `judges-2026` row. After that the cloud explanations in the submitted build stop working (Private only mode, with the on-device model, still works). Do this as soon as judging ends, and immediately if you think the token leaked.

### Know the risks

- **The token is inside the zip.** Anyone who downloads the extension can read it. Treat it as public until you revoke it.
- **What it allows.** It lets a caller pass App Check for your project, so they can use Firebase AI Logic on your Gemini quota until it is revoked. Keep the judging window short, set a budget alert or quota in Google Cloud, and watch usage.
- **Distribution.** Prefer an unlisted or private Web Store listing, or a GitHub release only for the judging period.
- **Never put the token in the README, the demo video, the Devpost text or a commit.** The panel's console prints it (`Firebase App Check debug token: ...`) when it opens, so do not film the console.
- The submission manifest's content script runs on `localhost:5173` and on `https://onboarding-xray.web.app` and `https://onboarding-xray.firebaseapp.com` (the default Firebase Hosting URLs for the hosted demo). It requests no other site access.

## Welcome page and tour

`welcome.html` opens automatically on install (`chrome.runtime.onInstalled`) and any time you click the **?** button in the side panel header. It has three steps and works the same in the dev and submission builds (it does not use Firebase).

1. **Check your setup.** Shows your Chrome version (the on-device model needs 139+) and the on-device model status. If the model is downloadable, **Download on-device model** starts the download with a progress bar (Chrome needs a click for this). It explains that Cloud mode keeps working meanwhile and that **Private only** needs the model.
2. **Try it: your first trace.** Opens the demo store (`https://onboarding-xray.web.app`, or `http://localhost:5173`) and asks you to Alt+click **Place order** on the checkout page. The page listens for the content script's messages and shows a success state with the chain when a traced element is clicked. **Open the side panel** opens the panel from the page.
3. **Use your own project.**
   - **Analyze:** `npm run analyze -- --backend path/to/backend --frontend path/to/frontend --no-copy` writes `analyzer/out/graph.json` and leaves the bundled demo graph alone.
   - **Tag** your frontend with the Vite plugin (`demo-app/frontend/plugins/dataSource.ts`).
   - **Load graph.json:** choose the file. It is validated, stored in the extension's IndexedDB, and the side panel switches to it (banner: "Showing your graph", **Use demo graph** to go back). Explanations of your own code never go to the shared Firestore cache.
   - **Enable on your app:** enter your app's address; Chrome asks for permission for that one site (optional host permission), and the content script is registered there. Reload the app's tab, then Alt+click. Remove a site with **Remove**.

The demo origins (`localhost:5173`, the two default Firebase Hosting URLs) are always enabled via the manifest. The hosted demo link only works after the demo is deployed to Firebase Hosting.
